## Findings

### 1. Medium: an unrelated tab group with the same display name makes Open puzzle target the wrong group

`openPuzzle()` queries every tab group in the current window, calls `findRoundGroup(name,
groups)`, and returns after focusing the first title match:

- `extension/src/background.js:519-527`
- `extension/src/lib/groupColour.js:30-34`

The match is only a trimmed, case-insensitive display name. It carries no hunt id, puzzle
id, sheet id, or marker that the group was created by Puzzle Chat. Consequently, any of
these can intercept the new action:

- a user-created group named after the puzzle;
- a round group with the same name as the puzzle;
- a different puzzle with the same name in this or another hunt.

In those cases, **Open puzzle as a tab group** focuses the unrelated group and returns
without opening either requested URL. The existing tests cover action payload validation
and colour/name matching, but not identity collisions at the `openPuzzle()` dispatch point.

Recommended correction: identify reusable puzzle groups by puzzle/sheet identity rather
than title alone. If browser tab-group metadata cannot carry that identity, derive it from
the group's tracked sheet tab and only reuse when its spreadsheet id matches; otherwise
create a distinct group.

### 2. Medium: the public privacy policy says the extension never reads a hunt-page address, but it receives and parses that address

The policy states:

> It never reads the address or content of hunt pages.

Evidence:

- `frontend/src/pages/Privacy.tsx:89-92`
- `frontend/src/lib/extension.ts:35-36,49-59,70-79`
- `extension/src/lib/actions.js:9-18,37-49`
- `extension/src/background.js:519-543,625-638`

The dashboard sends `puzzleUrl` to the extension. Both dashboard and extension parse and
validate it, and the background script passes it to `tabs.create()`. The extension does not
have general hunt-site host access and therefore normally cannot inspect the opened tab's
URL or contents afterward, but the current absolute statement is still inaccurate.

Recommended wording: say that the extension receives the hunt-page address the user clicks
so it can open the page, does not request host access to hunt sites, and does not read hunt-page
contents.

The test at `frontend/src/pages/Privacy.test.tsx:27` currently pins the inaccurate sentence
rather than checking a behavior-derived disclosure.

### 3. Low: the privacy policy's last-updated date was not advanced with the disclosure change

The policy was materially changed on 16 November to cover Firefox and hunt pages, but it
still displays `Last updated: 7 November 2026`:

- `frontend/src/pages/Privacy.tsx:25-28`
- `frontend/src/pages/Privacy.tsx:116-117`
- `frontend/src/pages/Privacy.test.tsx:19`

The page itself promises that the date at the top shows when the policy changes. The test
currently freezes the stale date.

Recommended correction: change both the page and its test to 16 November 2026.

### 4. Low: the extension README understates which hunt-page tabs Close solved will close

The developer README says Close solved also closes hunt pages opened by **Open puzzle as a
tab group**, "but not pages opened any other way":

- `extension/README.md:90-98`

Version 1.1 also records pages opened through the dashboard's ordinary **Puzzle page** link,
and `closeSolved()` closes those too:

- `extension/src/background.js:537-548,551-620`
- `docs/user-guide.md:365-382`

The user guide and store listing reflect the expanded behavior, but the implementation
reference does not. This can mislead release smoke testing and future maintenance.

Recommended correction: make the README match the user guide: both dashboard entry points
are remembered and eligible for Close solved; pages opened from Discord, Sheets, or modified
clicks are not.

## Firefox compatibility review

The generated Firefox manifest is structurally consistent with Mozilla's current WebExtension
documentation:

- Firefox MV3 uses `background.scripts`, and `type: "module"` enables ES module imports:
  <https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background>
- Firefox 139 introduced the `tabGroups` API; the manifest requests the required
  `tabGroups` permission, and the declared floor is Firefox 140:
  <https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/139>
- `sidebar_action` and `sidebarAction.toggle()` are the Firefox sidebar surface:
  <https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/sidebarAction>
- Manifest V3 signing requires a Gecko id, and current AMO submissions require
  `data_collection_permissions` declarations:
  <https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings>
- `storage.session` is in-memory browser-session storage and is cleared when the browser
  stops:
  <https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/session>

The generated manifest contained the expected 1.1.0 version, module background event page,
sidebar, options UI, Gecko id, Firefox 140 floor, data declarations, and shared permissions.
Both Chrome and Firefox archives contained the expected explicit source/assets and full
license, and passed ZIP integrity checks.

No additional source-level defect was found in the Firefox manifest transform, sidebar host,
Sheets-permission recovery, or Firefox websocket-origin path.
