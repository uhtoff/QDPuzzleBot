# M3.5 — Discord channel-adapter extraction (design)

**Status:** design approved, ready for implementation plan
**Milestone:** M3.5 (off critical path; deps: M3)
**Date:** 2026-06-23

## Goal

Finish the "all operations live in `bot/core/`" goal that M3 started. M3 left the
create paths (`web_create_puzzle`/`web_create_round`) and the pinned-info render as
ctx-free cog edge-helpers because relocating them cleanly first required the Discord
channel/category-management helpers (`get_or_create_channel`, `clean_name`, divider
logic) to be extracted. This milestone does that extraction, then promotes
`create_puzzle`/`create_round` and the pinned-info render onto the core engine, and
**full-strangles** the bang create paths (`_round_impl`, `create_puzzle_channel`) onto
the new core methods — the same pattern M3 used for solve/retag.

## Architecture

Two entry points (the Discord **bang edge** in `bot/cogs/puzzles.py`, and the **web
edge** in `bot/web/actions.py`) call into one central engine (`PuzzleService` +
helpers in `bot/core/`). Core performs the operation and its *intrinsic* effects (DB,
Google Sheets, Discord channel/category lifecycle) and **raises** on failure. Edges own
caller-acknowledgement and error-tolerance policy.

### Return-signal vs notification (the central distinction)

The Discord bang edge today fuses two things that are conceptually separate:

- **Notification** — a per-channel Discord artifact every channel watcher must see,
  *regardless of who triggered the operation* (pinned-info refresh, welcome message,
  solve/partial/unsolve message). This is "Discord-as-dashboard": a clunky-but-useful
  way of making Discord reflect state on a per-channel basis.
- **Return signal / caller-ack** — feedback only the invoker needs (the bang
  `ctx.send(":white_check_mark: …")` confirmation; the web edge's HTTP/JSON response →
  SPA toast).

M3.5 splits these. Notifications fire from core via an **injected notifier**, so they
happen identically no matter the caller. Caller-acks stay at their edge. Concretely: a
web-triggered `move_to_meta` will **not** spam Discord with a "moved" ack, but a
web-triggered `solve` **will** still emit the solve notification into the Discord
channel (and, once dashboard push lands, to the dashboard too).

## New core modules

### `bot/core/discord_channels.py` — ctx-free channel/category adapter

Pure Discord-lifecycle helpers with `guild` passed explicitly (no `ctx`,
no `self.environment`):

- `clean_name(name)` — relocated from the cog (`puzzles.py:267`).
- `get_or_create_channel(guild, category, channel_name, channel_type, **kwargs)` —
  relocated from `puzzles.py:1689`.
- `solve_divider_position(category)` / `first_channel_position(category)` — today's
  `get_solve_divider_position`/`get_first_channel` (`:920-927`) minus `ctx`.
- `clone_category_for_round(guild, ref_category, name, position)` + the
  `SOLVE_DIVIDER` divider-channel creation (the block shared by `web_create_round`
  `:850-856` and `_round_impl` `:1357-1363`).
- Constants/locks that belong to channel lifecycle move (or are passed): `SOLVE_DIVIDER`,
  `SOLVE_CATEGORY`, `MAX_CHANNELS_PER_GUILD`, `MAX_CHANNELS_PER_CATEGORY`,
  `MAX_CATEGORIES`. The shared `position_lock` stays a **single** instance to preserve
  current concurrency guarantees (pass it in or hang it off the service).

The cog keeps thin wrappers delegating to this module during the transition so existing
call sites (`:465`, `:473`, `:775`, `:853`, `:1091`, `:1360`, `:1385`) keep working.

### `bot/core/notifier.py` — injected presenter

- **`Notifier`** interface (protocol/ABC): `puzzle_created`, `welcome`, `refresh_info`,
  `puzzle_solved`. (`partial`/`unsolve`/`*_to_meta` can be added as those edges are
  unified later; only what M3.5 needs is defined now.)
- **`DiscordNotifier(bot)`** — the single ctx-free implementation. New home of the
  relocated `send_initial_*` render logic and `_web_render_info`/`web_refresh_info`.
  Fires the per-channel Discord notifications regardless of caller.
- **`NullNotifier`** — no-op implementation, used by tests and any caller that wants to
  suppress Discord output (e.g. `web_create_puzzle`'s `send_welcome=False` case becomes
  "pass a NullNotifier" or a flag on the call).

### Decoupling the render from `ctx`

The `send_initial_*` handlers already take their data via kwargs (`hunt`, `hunt_round`,
`puzzle`) — the web path uses that today via a synthetic `ctx`. The only remaining `ctx`
uses are three helpers: `_add_puzzle_links_field(ctx, …)`, `_overview_url(ctx, hunt)`,
`_build_embed_list(ctx, …)`. M3.5 threads `guild`/`guild_data`/`gsheet_cog` through
these explicitly so the render is fully ctx-free, then it lives in `DiscordNotifier`.
The `self.environment[ctx.message.id]` synthetic-ctx hack (`_web_render_info` `:670`)
is deleted.

## `PuzzleService` additions

Mirroring how `solve`/`move_to_meta` already live in the service:

- `create_puzzle(guild, hunt, round_data, name, is_meta, notifier)` — space checks → DB
  row + Google sheet + channel via `discord_channels` → `notifier.welcome(...)`. Raises
  `RuntimeError("<code>")` on recoverable problems. **Orphan cleanup on failure** — the
  current `_cleanup_orphan_puzzle` (`:803`) moves into core unchanged in behaviour.
- `create_round(guild, hunt, name, notifier)` — duplicate/space checks → clone category
  → `create_puzzle(is_meta=True)` → round row + `meta_code`/`meta_id` → meta welcome.
  Returns `(RoundData, PuzzleData)`. Full rollback on failure (round row + orphan puzzle
  + orphan category), matching today's `web_create_round` `:870-891`.

## Strangle plan

- `web_create_puzzle`/`web_create_round` collapse to thin `actions.py` calls into the
  service (passing a `DiscordNotifier`). The swallowing `web_refresh_meta` wrapper
  (`:656`) is removed — callers use `service.refresh_meta`/`refresh_metas` directly with
  edge-side tolerance.
- `create_puzzle_channel` (`:1078`) and `_round_impl` (`:1317`) are rewritten to call
  `service.create_puzzle`/`create_round`; the divergent duplicate orchestration is
  **deleted**. The bang edge keeps only its `ctx.send` invoker acks and command-specific
  routing (`command_map`).

## Forward compatibility (out of scope to implement)

Dashboard push notifications are a separate effort on their own thread. The `Notifier`
interface is the seam for it: when push lands it adds a `WebNotifier`/`DashboardNotifier`
implementing the same contract. A `CompositeNotifier` (fan-out) then lets core notify
**both** surfaces from one call, so a single `service.solve(...)` reaches Discord channel
watchers and dashboard users symmetrically. The return-signal/notification split still
holds: the composite handles cross-surface *notifications*; per-caller acks stay at their
edge (no double-ack). **M3.5 designs for this but builds only `DiscordNotifier` +
`NullNotifier`.**

## Testing

- **Equivalence** (M3 discipline): assert bang-path and web-path create produce the same
  DB rows / sheet calls / notifier calls, using a `NullNotifier` + a recording spy — no
  Discord mocks needed in core tests.
- **Unit**: `discord_channels` helpers (`clean_name`, divider/first-channel position) are
  pure → direct tests.
- **Regression**: keep `tests/test_create_orphan_cleanup.py` green against the relocated
  cleanup; keep `tests/test_solve_equivalence.py` style coverage for create.

## Constraints / things not to change

- Preserve the **migration → deploy → code** rule (no schema change in M3.5; none needed).
- `position_lock` stays a single shared instance — do not introduce a second lock.
- No behaviour change to the orphan-cleanup / rollback semantics; only their location.
- Don't touch unrelated cog commands or the M5/M6/M7 rollup paths.

## Phasing (each a reviewable commit)

0. Reset this worktree onto local `main` (per the worktree-base note: `origin/main` is
   intentionally stale) before starting.
1. Extract `discord_channels.py`; cog helpers delegate to it (no behaviour change).
2. Decouple `send_initial_*` from `ctx`; introduce `notifier.py` (`DiscordNotifier` +
   `NullNotifier`); re-express `web_refresh_info`/`_web_render_info` via `DiscordNotifier`.
3. Add `service.create_puzzle`/`create_round` + relocated orphan cleanup; strangle the
   web edges onto them.
4. Strangle bang `create_puzzle_channel`/`_round_impl`; delete the divergent twins.
5. Equivalence + unit tests; mark M3.5 done in `docs/PLANS.md`.

## Acceptance criteria

- `clean_name`, `get_or_create_channel`, divider/category helpers live in
  `bot/core/discord_channels.py`; cog has only thin delegators (or call sites updated).
- `PuzzleService.create_puzzle`/`create_round` are the single create implementation;
  both bang and web edges call them; divergent twins deleted.
- Pinned-info/welcome/solve render is ctx-free and fired through `DiscordNotifier` from
  core; the synthetic-ctx hack is gone.
- Notifications fire regardless of caller; caller-acks remain edge-local (web move-to-meta
  does not post a Discord ack).
- Equivalence + unit tests pass; orphan-cleanup regression stays green.
